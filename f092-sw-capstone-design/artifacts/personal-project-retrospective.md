# [SW캡스톤 개별소회] 팀 5Stone 하장한

## 프로젝트 회고

* 초기 설계에서는 에이전트의 대화 흐름을 명시적으로 제어하고 예측 가능성을 높이기 위해 Workflow를 FSM(유한 상태 기계) 기반으로 정의했다. 하지만 이는 결과적으로 Workflow가 구체적인 비즈니스 로직 절차를 담지 못하고, 단순히 Slot을 수집하는 추상적인 레벨에 머무르게 만드는 한계를 보였다. 차라리 Slot의 To-Do List 형태로 단순화하는 것이 낫지 않았을까 하는 아쉬움이 남는다. 
  돌이켜보면, Workflow라는 별도의 상태 전이 속성을 두기보다는 Data-Driven 접근을 취하는 것이 아키텍처 측면에서 훨씬 유연했을 것이다. 예를 들어, Slot을 단순한 데이터 컨테이너가 아닌 로직을 포함한 객체로 격상시키고, Slot 간에 AND, OR, XOR 같은 논리 연산자와 위계 관계를 정의할 수 있다. 탈출 조건 역시 Slot 간의 연산을 통해 선언적으로 구성했다면, Workflow는 런타임 중 Slot 리스트를 해석하여 파생되는 인스턴스에 불과해진다. 이러한 함수적 접근을 취했다면 Airflow 파이프라인에서 Workflow를 산출하는 과정도 단순히 YAML 파일을 채우는 수준으로 단순화되고, 백엔드와 파이프라인 간의 인터페이스도 상당 부분 덜어낼 수 있었을 것이다.
  * 이 부분은 프로젝트의 시작 자체가 채널톡이라는 플랫폼의 워크플로우를 모방한 것이다보니 발생하는 흔적기관에 가깝다고 생각한다. 사람이 직접 작성하는 것보다는 llm이 작성하는 것이 메인이 되는 환경에서, 직관적이라는 이유만으로 절차적 방식을 고수할 필요는 없다고 생각한다. 
  * 현재는 policy, risk를 일종의 Cross-Cutting Layer로 간주하고 있어 평가가 트리거된 구체적인 원인 객체와 시점을 파악하기 힘든 추적성 상의 맹점이 발생한다. Data-Driven 방식을 채택했다면 Slot 클래스 자체에 AOP를 적용해 런타임 도중에 Slot 데이터가 갱신되는 구체적인 타이밍을 로그 상에 명시적으로 기록할 수 있었을 것이다.
* 현재 Domain Pack은 Intent, Workflow, Slot, Policy, Risk가 각각 독립된 관계형 테이블로 정규화되어 있다. 그러나 런타임을 보면 Intent-Workflow-Slot은 강한 생명주기를 공유하며 결합하는 반면, Policy와 Risk는 전역적 Cross-Cutting Concern으로 별개 동작한다. 같은 정규화 체계 안에 성격이 다른 두 축이 섞여 임피던스 불일치가 발생하는 셈이다.
  돌이켜보면, 앞서 회고한 Workflow 제거 방향과 함께 영속성 계층을 런타임 응집도에 맞춰 재정렬했으면 더 깔끔했다. 구체적으로는 Intent와 Slot을 핵심 축으로 남기고, Workflow가 담당하던 분기·순서·종료 로직은 Escape Condition이라는 별도 junction 테이블로 정규화하여 현재 `intent_slot_binding`과 동일한 패턴(Slot 간 논리 연산자 AND/OR/XOR와 탈출 조건을 선언)으로 Intent에 바인딩한다. 반면 Policy와 Risk는 앞서 언급한 AOP 인터셉터 패턴으로 분리해 Slot 테이블과의 직접적 FK 의존을 제거한다. 이렇게 하면 핵심 도메인과 관심사가 테이블 레벨에서도 명확히 분리되어, 런타임 동작과 데이터 모델이 정확히 일치하는 직관적 구조가 된다.
* 현재의 ML 파이프라인은 Intent-First 접근법을 채택하고 있다. `.agent/docs/ml-pipeline-evolution.md`에서 기록된 바와 같이, 이 구조의 한계는 추상적인 Intent 자체에 처리 절차에 대한 정보가 내포되어 있지 않다는 점이다. 이로 인해 `intent_discovery` 이후 `flow_splitting`·`draft_generation`에서 Slot과 Workflow를 Intent 발견 결과로부터 파생 생성해야 하는 순차적 의존성이 발생하며, Intent 발견의 품질 편차가 하위 컴포넌트 전체로 Cascading되는 구조적 취약성을 갖는다.
  이 문제를 근본적으로 해소하려면, 추상적인 Intent가 아닌 구체적인 데이터인 Slot을 1급 시민으로 간주하는 접근으로의 전환이 필요하다. 실제 대화 로그에서 추출된 Slot 집합을 기준으로 1차 클러스터링을 수행하고, 도출된 군집 내에서 고객의 의도(Intent)를 세분화하는 바텀업 파이프라인이 모델링 측면에서 더 타당하다. 동일한 Slot 집합을 공유하는 대화들은 유사한 비즈니스 처리 절차를 밟을 확률이 높기 때문에, Slot 집합이 곧 암시적 처리 절차의 프록시가 되어 일관성 높은 탈출 조건을 함께 발견할 수 있다.
  물론 전제되어야 할 과제도 있다. 현재 파이프라인은 대화에서 Slot을 자동 추출하는 전용 stage가 없고, `draft_generation`에서 `workflow_signal` flag를 정적 매핑해 Slot을 생성할 뿐이다. Slot-First가 성립하려면 대화 로그로부터 구체적인 정보 항목을 식별하는 Slot extraction 역량이 선행되어야 한다. 또한 Slot이 수집되기 전 이탈한 대화를 분류하기 어렵다는 트레이드오프도 존재한다. 그럼에도 파이프라인의 복잡성 지점을 "의미 유사성 기반 군집의 오류 복구"에서 "구체적 정보 항목 탐지"로 재배치함으로써, 실질적인 비즈니스 로직 단위로 데이터를 묶어낼 수 있다는 점에서 Slot-First 구조는 검토할 가치가 있는 방향이다.

## 개인적인 회고

* **프로젝트 경험:**
  이전에도 데이터베이스, 기계학습, 시스템프로그래밍및실습 과목 등에서 기말 프로젝트를 진행한 경험이 있었으나, 한 한기를 온전히 프로젝트 하나에만 집중했던 경험은 없었다. 이전까지의 과목 프로젝트가 학점 취득이라는 궁극적인 목표 아래에 기말고사와 조율되는 수업의 일부였다면, 그러나 캡스톤 프로젝트는 다른 것들과는 달리, 서비스의 초기 기획부터 실제 배포에 이르는 소프트웨어 생애 주기(Software Life Cycle) 전반을 온전히 경험할 수 있는 기회였다. 비록 장기적인 유지보수 단계까지 나아가지는 못했지만, 제로 베이스에서 출발해 하나의 프로덕트를 세상에 내놓기까지의 모든 과정을 한 학기 동안 밀도 있게 밟아볼 수 있었다. 이처럼 온전한 프로젝트 주기를 거치며, 단순한 기능 구현을 넘어 실무적인 관점에서 시스템을 구축하는 방법을 배울 수 있었다.
* **서비스 기획 경험:**
  이전까지 프로젝트에서 수행했던 기획은 사실 어떤 아이디어가 팀원들의 마음에 더 꽂히는지까지만 다루는, 직감의 영역에 가까웠다. 이번 프로젝트 역시 실제 설문, 정량적인 리서치 단계까지 나아가지는 못했다. 하지만 결정적으로 차별화되는 점은 추상적인 이미지에서 구체적인 개발까지의 미싱 링크가 최소화됐다는 점이다. 기존의 '아이디어 스케치' 수준을 넘어, 시스템이 어떻게 동작하고 구현되어야 하는지를 체계적으로 구성할 수 있었다. 유저의 페르소나를 정의하고, User Journey 기법을 통해 단순히 '좋은 기능'을 나열하는 대신, 서비스를 실제로 이용할 이해관계자를 '최종 고객', '고객지원 운영 책임자', '현업 정책 담당자'로 세분화하여 페르소나를 정의했다. 각 페르소나의 목표와 페인 포인트를 분석한 뒤, 문제 발생부터 해결에 이르는 과정을 Happy Path, Exception Path, Failure Path 등 구체적인 User Journey로 구성했다. 이를 통해 챗봇이 어떤 상황에서 AI 기반으로 자동 응답을 하고, 어떤 크리티컬한 예외 상황에서 현업 담당자에게 권한을 이관해야 하는지 시스템의 역할과 한계를 명확히 설정할 수 있었다. 그려진 User Journey를 바탕으로 기획을 시스템의 요구사항으로 변환하는 User Story Mapping을 진행했다. 전체 시스템 흐름을 '데이터 기반 구축', 'ML 기반 지식 추출', '정책 기반 실시간 실행' 등의 굵직한 Epic으로 나누었다. 이후 각 Epic 하위에 "나는 시스템으로서, 분류할 수 없는 문의를 안전하게 후속 단계로 넘기고 싶다"와 같이 주체와 목적이 뚜렷한 User Story를 도출하여, 우리가 개발해야 할 목표가 사용자 관점에서 어떤 가치를 지니는지 구조화할 수 있었다. 기획과 개발 사이의 미싱 링크를 완전히 없앤 핵심은 Task Breakdown 과정이었다. User Story만으로는 실제 개발 기준으로 삼기 불충분하다는 것을 깨닫고, 각 스토리마다 "응답 지연이 2초 이내이다", "정확도가 90% 이상이다"와 같이 성공 여부를 판가름할 구체적인 Acceptance Criteria을 작성했다. 나아가 이를 달성하기 위해 프론트엔드, 백엔드, AI, QA 등 역할별로구현 가능한 최소 단위의 Task로 세분화하여 Product Backlog를 구성했다. 결과적으로 이번 기획 과정은 직감을 설득하는 과정이 아니라, 비즈니스의 목표를 구체적인 시스템의 언어로 번역하고, 이를 다시 개별 개발자의 구체적인 과업으로 안전하게 분배하는 과정이었음을 배울 수 있었다.
* **체계적인 협업 경험:** 
  이전 팀 프로젝트에서는 Git을 본격적으로 사용해볼 기회가 적었다. 역할을 완전히 분담하는 분업 체계로 작업하거나, 주피터 노트북과 구글 드라이브만으로도 해결되는 수준의 소규모 프로젝트가 대부분이었기 때문이다. 그렇기 때문에 체계적인 협업 경험의 부재가 학기 초 목표했던 최우선 극복 과제였다. 하지만 이번 프로젝트를 통해 그 한계를 성공적으로 극복할 수 있었다. 브랜치 기반의 독립적인 작업공간을 확보하고, Pull Request를 통해 작성한 코드를 리뷰하고 통합하는 과정을 거쳤다. 더 나아가 TDD, SDD와 같은 특정 개발 방법론을 실무적으로 적용하며 Git, Github을 아카이브 정도로 활용하던 이전과 달리 협업 툴로서 운용하는 시각을 갖출 수 있게 되었다.
* **체계적인 코드 품질 관리:**
  이전의 코드 품질 관리는 실제 버그가 발생한 이후의 수정, 버그가 발생하는 루트의 회피와 같은 대응적인 조치에 한정하거나, 셀프 리뷰, 코드 전문을 웹기반 ai에 붙여넣고 리뷰를 부탁하는 등의 주먹구구식의 관리에만 급급했다. 그렇다 보니 어디서부터 꼬인 것인지, 어떻게 처리할지, 이 코드를 건드려도 되는 것인가에 대한 비생산적인 고찰들이 작업의 후반부를 잠식하고 있었다. 공수를 작업물의 UX 개선, 발표 준비와 같은 생산적인 방향으로 투자하지 못하고 지난 기간 방치한 기술 부채를 청산하는데 시간을 쏟고 있었던 것이다. 제일 큰 문제는 스스로가 이 과정 또한 개발의 일부라고 생각하며 타협하고 있었다는 것이다. 이번 프로젝트에서는 다른 팀원(강희원)의 주도로, SDD, TDD와 CI, PR 파이프라인을 도입하고, 개인적으로는 단일 에이전트 의존에서 벗어나 에이전트 파이프라인을 이용해 이러한 문제를 극복할 수 있었다. 코드 컨벤션 관리 등을 Spotless, Linter 등에 위임하고, TDD를 도입해 테스트 코드의 작성을 핵심적인 과업으로 체화했다. 또한, CI 파이프라인에 SonarQube 등을 통합해 테스트 커버리지, 그외의 정적인 문제를 선제적으로 색출해 품질을 끌어올릴 수 있었다. 개인적으로는 에이전트 파이프라인에 Playwright MCP, SonarQube MCP를 통합해 정적인 문제와 런타임 문제를 선제적으로 색출하게 했다. PR 단계에서는 CodeRabbit와 같은 코드 리뷰 에이전트를 통합해 코드의 품질을 관리했다. 개인적으로는 Coderabbit의 리뷰까지 파이프라인으로 흡수해 에이전트의 산출물과 실제 코드 사이에 정합성을 유지하기 위해 노력했다. 최종적으로는 Ai는 동료가 아니라, 정확한 컨텍스트가 주어져야만 올바른 결과를 내는 '함수'와 같다는 것을 배울 수 있었다. 여러 시스템적인 요소 덕분에, 유지보수와 디버깅에 쏟던 시간을 프로덕트의 UX 개선과 시연 준비에 온전히 투자하며 성공적으로 프로젝트를 마무리할 수 있었다.
